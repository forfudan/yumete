# Documentation and translations

## Sources and organization

`docs/en/SUMMARY.md` defines the reading order. Each chapter in `manual/` is an
independent topic. Early chapters teach the editing model; later chapters explain
writing workflows; commands and configuration are reference chapters. Use relative
Markdown links for cross references, including `file.md#heading` fragments.

`docs/manual.md` is the compatibility entry point. Edit the topic files rather than
adding material to that entry point. README is the project introduction, CHANGELOG
records user-visible changes by release, and `licenses/` preserves third-party
notices. The build includes these repository documents as appendices.

## Build and check

Use Python 3.11 or newer, OpenCC, and mdBook. OpenCC is required for translation
checking even when building only the English book. Install it with
`brew install opencc` on macOS or `apt-get install opencc` on Debian/Ubuntu.
A regular mdBook 0.4.52 installation is sufficient for HTML and the default PDF
backend (`cargo install mdbook --version 0.4.52 --locked`).

```sh
python3 scripts/docs.py check
python3 scripts/docs.py build
python3 scripts/docs.py build --lang en
python3 scripts/docs.py build --pdf
python3 scripts/docs.py build --pdf --backend default
python3 scripts/docs.py build --pdf --backend mdbook-pandoc --lang en
python3 scripts/docs.py build --pdf --backend mdbook-pdf --lang en
python3 scripts/docs.py build --pdf --backend mdbook-typst --lang en
```

Without `--lang`, every language is built. `--backend` requires `build --pdf`;
HTML-only builds do not need PDF tools or fonts. Every PDF backend also builds
the searchable HTML book from the same Markdown and appendices.

Output goes to `docs/book/<language>/`:

| Backend | PDF filename | Pipeline |
| --- | --- | --- |
| `default` (also used when omitted) | `yumete.pdf` | mdBook HTML → Chrome print |
| `mdbook-pandoc` | `yumete-mdbook-pandoc.pdf` | Pandoc → LaTeX → Tectonic |
| `mdbook-pdf` | `yumete-mdbook-pdf.pdf` | mdBook PDF renderer → Chrome |
| `mdbook-typst` | `yumete-mdbook-typst.pdf` | mdBook Typst renderer → Typst |

Switching backends, or rebuilding HTML, retains PDFs already generated by other
backends. The script builds in a temporary directory; a renderer failure leaves
the previous book intact. The CI workflow builds every language with `default`
and checks the configuration and routing of all four backends in the tool tests.

## PDF backends

The plugin versions below were tested together. Their mdBook JSON interfaces
are not interchangeable: `mdbook-pdf` 0.1.13 needs mdBook 0.5, while the pinned
Pandoc and Typst renderers use mdBook 0.4. The script checks this before building.

| Backend | Renderer | mdBook | Additional tools |
| --- | --- | --- | --- |
| `default` | none | 0.4 or 0.5 | Chrome/Chromium |
| `mdbook-pandoc` | 0.10.0 | 0.4.52 | Pandoc 3.x, Tectonic 0.17, Fontconfig |
| `mdbook-pdf` | 0.1.13 | 0.5.2 | Chrome/Chromium |
| `mdbook-typst` | 0.1.10 | 0.4.52 | Typst 0.15.1 |

Install only the renderer you intend to use:

```sh
cargo install mdbook-pandoc --version 0.10.0 --locked
cargo install mdbook-pdf --version 0.1.13 --locked
cargo install mdbook-typst --version 0.1.10 --locked
```

Keep both mdBook drivers in separate locations when using all backends:

```sh
cargo install mdbook --version 0.4.52 --locked --root "$HOME/.local/share/yumete-docs/mdbook-0.4"
cargo install mdbook --version 0.5.2 --locked --root "$HOME/.local/share/yumete-docs/mdbook-0.5"
export MDBOOK_04="$HOME/.local/share/yumete-docs/mdbook-0.4/bin/mdbook"
export MDBOOK_05="$HOME/.local/share/yumete-docs/mdbook-0.5/bin/mdbook"
export PATH="$HOME/.cargo/bin:$PATH"
```

`MDBOOK` overrides the driver for every backend. Otherwise, the script uses
`MDBOOK_04` or `MDBOOK_05` for the required series, then falls back to `mdbook`
on `PATH`. It never replaces your global mdBook installation. Prebuilt drivers
are available from [mdBook releases](https://github.com/rust-lang/mdBook/releases).
Set `CHROME` to the Chrome/Chromium executable if automatic discovery cannot find
it; this applies to both Chrome-based backends. The PDF outline is enabled for
sidebar navigation in macOS Preview and other readers.

### macOS tools and fonts

```sh
# default or mdbook-pdf: install Google Chrome or Chromium, then optionally set CHROME.
# mdbook-pandoc:
brew install pandoc tectonic fontconfig
brew install --cask font-dejavu
# mdbook-typst:
brew install typst
```

The `macos` font profile uses DejaVu Sans and DejaVu Sans Mono for Pandoc, and
Times New Roman and Menlo for Typst. Chinese examples use PingFang SC; the TeX
symbol fallback uses Arial Unicode MS. The font checker reports any missing
families. Install the missing fonts or select installed families in
`docs/backends/fonts.toml`.

### Linux tools and fonts

```sh
sudo apt-get update
sudo apt-get install -y opencc pandoc fontconfig fonts-dejavu-core fonts-noto-cjk fonts-noto-core
```

For the Chrome-based backends, install Google Chrome or Chromium and set `CHROME`
if necessary. For the Pandoc backend, install the prebuilt executable from
[Tectonic releases](https://github.com/tectonic-typesetting/tectonic/releases)
on `PATH`; for the Typst backend, do the same from
[Typst releases](https://github.com/typst/typst/releases). The `linux` profile uses
DejaVu fonts, Noto Sans CJK SC, and Noto Sans Symbols 2.

On Windows, install the corresponding executables and fonts on `PATH`, set the
mdBook driver paths (including `.exe`), and select matching installed font
families in `fonts.toml`. `CHROME` also accepts a full Windows executable path.

Tectonic downloads its TeX packages on first use; this can take several minutes
and requires network access. The browser backends do not require a TeX installation.

### Configuration

The four `docs/backends/<backend>.toml` files declare driver compatibility,
required tools, the renderer's own options, and its result path. Tool paths are
resolved at build time; no machine-specific executable paths are stored there.
The temporary mdBook configuration combines their `[output.*]` sections with the
shared HTML configuration. `default.toml` also holds the Chrome print arguments.

`docs/backends/fonts.toml` contains installed font family names. The profile is
`macos` on macOS and `linux` elsewhere; set `DOCS_FONT_PROFILE` to select another
profile, including one you add to that file. Font families are checked before
rendering rather than silently substituted. Font changes do not affect browser
PDFs, which use the fallback fonts in the print stylesheet.

`pandoc-header.tex` wraps highlighted code and permits inline breaks at command
separators. `typst-header.typ` configures code fonts and wrapping. The script
expands font and tool placeholders when staging the backend configuration.
A4 is the default paper size for all backends.

The renderers produce different layouts and outline structures. In particular,
mdbook-typst 0.1.10 can repeat chapter headings in the body and outline; the
configuration preserves the plugin's chapter handling. Some long inline code in
the Pandoc output can still need layout adjustment. Choose a backend after
checking the exported book, especially its tables and Chinese examples.

## Help lookup

The core build embeds Markdown directly from these source directories. No Python,
mdBook, browser, network, or external manual is needed to use installed help.
Command names and aliases come from the parser's command table. Option locations
come from TOML examples, and key locations from reference tables. Add a stable
`<!-- help: topic another-topic -->` marker to create explicit topic aliases.
Add `<!-- help-index: keys -->`, `<!-- help-index: commands -->`, or
`<!-- help-index: options -->` to identify reference tables and configuration
examples for indexing; filenames and chapter numbers do not affect lookup.
Keep tags language-neutral. Exact command/key/option lookups take precedence over
incidental mentions in prose. A matching translation must preserve the source's
identifiers and anchors. Relative links resolve within the embedded book.

The documentation checker validates local cross references and translation tags.
Existing Rust checks read the split English chapters in reading order and continue
to validate configuration examples, documented commands, and manual style.

## Translation policy

English (`en`) is the complete source. Simplified Chinese (`zh-Hans`) and
Traditional Chinese (`zh-Hant`) use the same relative page paths. Traditional Chinese is
the Chinese source; Simplified Chinese is generated by `python3 scripts/make_manual_sc.py`
using OpenCC. Never edit `docs/zh-Hans/` directly. Run the script after changing a
Traditional Chinese page; `--check` detects stale generated files in CI. Links, help
tags, explicit anchors, and `<!-- verbatim -->` blocks are preserved. A translation can
be added one page at a time; missing pages are taken from English and display a
notice, both in built books and in editor help. A fallback page is never stored as
a copied translation. Each language has a translated entry point and help guide.

Translate prose, link labels, and examples that are natural language. Preserve
command names, configuration keys, help tags, filenames, and link destinations.
For heading links, preserve the original anchor with an explicit HTML anchor if
the translated heading differs. Record `<!-- source-revision: COMMIT -->` in a
translated page, replacing `COMMIT` with the English revision reviewed. Review
translations when that source changes; a revision marker is a review aid, not a
claim of automatic synchronization. Review the Traditional Chinese translation against English before generating Simplified Chinese.
New languages require adding their code to `LANGUAGES` in `scripts/docs.py` and
the embedded-help build and language selector, plus a translated landing page.
